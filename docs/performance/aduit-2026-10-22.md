# 性能优化前后分析（2026-10-22）

本次主要收益来自精确事件路由索引和定向缓存失效。在相同的 512 路并发、每次 16 节点负载下，独立串行图总耗时降低 **38.94%**、吞吐提高 **63.78%**；独立并行图总耗时降低 **53.81%**、吞吐提高 **116.51%**。已有热链的复用图收益有限，复用串行图本轮耗时增加 2.20%，三档等待负载增加约 2–3%；本报告保留这些结果。

另外修复了并行子任务重复取消时的许可缺口，并补齐父分发取消、结束及超时恢复的清理路径。完整正确性测试 **977 passed**；84 个背压边界用例在 20 个独立进程中累计 **1,680 次通过**。

## 测量方法与版本

- 优化前：Git `9743814` 的独立源码副本；优化后：本次工作区实现。用户原有版本文件改动未纳入优化范围。
- 环境：Python 3.12.12；macOS-27.0.1-arm64-arm-64bit。保持 GC 开启，普通日志与分发打印关闭，保留 ERROR 日志。
- 四个独立进程依次运行 `before → after → after → before`。每个场景在每个进程中预热一轮、测量三轮；每版合计六个正式样本，表格使用中位数。每轮测量前执行 `gc.collect()`，计时期间使用正常 GC。
- 相同的输入、节点数、并发量、快照策略、背压和计时边界；逐个校验结果、状态、步数、快照数以及完成数量。测试结束检查分发任务清空、许可全数归还。
- 总耗时包含建图、context 与 task 准备、执行和返回结果复制；结果校验、剩余分发清理及图分解在计时之后。JSON 同时保存 build / prepare / execute 分项和纯执行吞吐。
- P50/P95/P99 从同批调用的共同启动门释放开始计时，再取各轮百分位数的中位数。它们描述这组集中提交任务的完成延迟，不能直接解释为外部服务的线上请求 P95。
- 事件循环延迟用 1 ms 定时任务采样；内存单独使用 tracemalloc 测量，时间样本不启用 tracemalloc。内存结果表示 Python 分配量，未测进程 RSS。未固定 CPU 核心，无网络或外部服务参与。

两个相同标签进程的运行时源码 SHA256 必须相同，脚本会检查；指纹排除版本文件，包含其余运行时 Python 源码。

## 路由微基准与缓存内存

| 场景 | 优化前 | 优化后 | 说明 |
| --- | ---: | ---: | --- |
| 512 个精确 handler，新名称无匹配 | 187.61 µs/查询 | 0.46 µs/查询 | 每轮 2,000 次不同名称查询 |
| 已缓存精确链查询 | 94.44 ns/查询 | 101.19 ns/查询 | 每轮 30,000 次查询 |
| 查询 50,000 个历史名后，精确订阅注册＋注销 | 32819.10 µs/对 | 2.96 µs/对 | 每轮 5 对取中位数；不含 handler 构造 |

冷查询每次约 **187.61 → 0.46 µs**，约为原来的 1/409。临时精确订阅增删从 **32.82 ms → 2.96 µs**。后者比较的是相同的 50,000 次历史名称查询，新实现实际保留 8,192 个缓存键；收益同时包含定向失效与缓存容量约束。该结果仅描述包内注册/注销成本，不包含请求响应、业务执行或网络耗时。

热查询约 **94.44 → 101.19 ns**，每次增加约 **6.76 ns**，相对增幅约 7.15%，属于刷新 LRU 等操作的成本。保留有界缓存，以换取长期内存和高基数临时订阅的稳定性。

| 场景 | 优化前 MiB | 优化后 MiB | 含义 |
| --- | ---: | ---: | --- |
| 30,000 个无匹配名称 | 5.07 | 2.03 | 查询后仍保留的 Python 分配 |
| 大状态 / 完整快照 | 27.47 | 27.47 | 构建、执行、校验期间的分配峰值 |
| 大状态 / 关闭快照 | 3.20 | 3.20 | 构建、执行、校验期间的分配峰值 |

链缓存使用 LRU，默认最多保留 **8,192** 个精确名称，空链也计入容量；上述保留量减少约 **59.94%**。共享 core 可通过 `PIPELINE.handler_chain_cache_size` 设置正整数容量。淘汰不会修改已经捕获的链或 handler 引用。事件观察历史仍按原有契约保留，路由缓存容量不等于整个运行时的总内存上限。

## 深拷贝和内部重复处理

已删除的冗余操作：

- `asyncio.gather()` 已返回列表，移除结果外层再次 `list()` 的分配，保持 task、gather 和取消传播方式。
- 快照目标已明确为字符串或字符串列表；改用字符串复用或列表浅拷贝，恢复目标也复用同一复制规则。
- 内部执行目标已在发布前验证，执行时保留跨 await 的列表冻结，省去再次遍历验证元素。
- 命名空间查询返回字符串或抛出异常，删除后面的不可达 None 兜底；注册表内部使用已维护的排序索引，删除冗余查询和不可能的分支。

保留状态、快照、命令及输出的必要隔离。普通节点返回的 Command 和顶层容器会在等待其他并行节点前被冻结，完整 state 复制则防止节点输入修改泄漏到共享状态；它们有具体的并发与恢复作用。

`GraphManager.compile_graph()` 现在透传已有的 `no_snapshot` 开关：

```python
graph = manager.compile_graph("start", no_snapshot=True)
```

在本次大状态负载中，新版本显式关闭快照的总耗时约 **201.29 → 109.11 ms**（减少约 **45.79%**），Python 分配峰值约 **27.47 → 3.20 MiB**（减少约 **88.37%**）。这项收益来自显式选择不保存快照；默认仍开启完整快照，普通结果的输入/输出隔离仍保留。关闭后无法从未保存的 checkpoint 恢复，abort 使用当时已提交的 live state。直接 NodeGraph 的旧版已有该选项，表格也按相同策略进行了前后对比。

## 背压、取消与死锁验证

确定性回归证明了旧实现的许可缺口：三个子任务共享一条前台链并进入 suspension；其他处理器耗尽许可后，先取消这些子任务，使最后一个停在 reacquire，再次取消。父 handler 用 `gather(return_exceptions=True)` 接住结果后，会在没有许可时继续。修复后，仍存活的 owner 需要继续执行时，子任务先恢复许可再传播取消；owner 取消或结束则及时清理其子任务的重获等待，避免互相等待。

独立缺陷复现使用当前测试基础，仅将 `event/base.py` 与 `event/event_loop.py` 替换为 `9743814` 的原文件，保留新 registry 供测试隔离 fixture 使用。选定的 16 个用例得到 **8 failed / 8 passed**；八处失败均为父 handler 在许可仍被占满时提前继续。这份取消缺陷证据的副本范围记录在 JSON 中；性能基准使用前述完整旧源码副本。

最终实现还保证处理器超时后，错误回调及没有错误回调时的下一前台 handler 都先恢复许可；不会因为子任务在 owner 取消期间退出而绕过容量限制。恢复等待复用现有信号量和锁，不额外创建 shield/acquire helper task。

新增 [边界测试](../../source/tests/integration/event/test_backpressure_boundaries.py) 覆盖实际 permits **1/2** × queue **1/2**，明确断言运行时容量确实生效：

- 所有许可耗尽、consumer 已持有 pending event、队列也全满时，父 handler 发布后续事件及阻塞的外部 producer 均可继续。
- 满载时的三层嵌套图、并行子分支，以及 received / processed 两种请求响应等待。
- LRU 淘汰、订阅替换/注销、consumer stop/start 不改变已经捕获的 handler references 和顺序。
- 在 suspend body、resume lock / semaphore reacquire 阶段取消；重复取消子任务、父分发首次/再次取消，均检查后续业务是否持有许可。
- 父分发结束时清理已经停在 reacquire 的 detached child；已结束后才离开 suspension 的旧子任务不重获许可。
- waiter 定时过期、处理器 timeout、错误回调和下一处理器的恢复；显式父级 suspension 包住可恢复 timeout。
- 每个场景结束检查全部许可归还、无 pending semaphore waiter、无 pending dispatch、队列为空、无残留分发/后台任务及回调异常。

父 handler 自行组织需要恢复后继续执行的 timeout 或并行等待时，使用父级 `suspend_process()` scope 负责借出与恢复许可。取消分发与恢复业务是不同的生命周期路径；任意应用层互相等待仍需要遵守这个容量借出规则。

| 检查 | 结果 |
| --- | --- |
| 完整正确性测试 | 977 passed in 7.92s，进程 deadline 90s |
| 背压、取消、订阅、handler execution 及新增边界 | 242 passed in 5.93s，进程 deadline 60s |
| 新增边界重复验证 | 20 个独立进程 × 84 cases = 1,680 passed，每进程 deadline 20s |
| 原有 13 组性能 workload 小规模验证 | 13 passed in 2.90s |
| Ruff / diff whitespace 检查 | 通过 |

异步场景本身还有 deadline，外层进程 watchdog 用于防止取消清理挂起。以上测试没有观察到死锁或许可泄漏；这是一组明确负载下的验证结果。
